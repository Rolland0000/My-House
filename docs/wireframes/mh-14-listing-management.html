Comportement

POST /listings
  • Champs requis (NOT NULL en DB) : titre, description, type, ville, prix (LIST-01). Surface, pièces et quartier sont nullables en base — traités comme facultatifs ici, même si LIST-01 les liste sans distinction.
  • Étape 2 « Photos » verrouillée : POST /media/upload exige un listing_id existant, donc l'annonce doit d'abord être créée.
  • 200/201 → déverrouille l'étape 2 et y navigue automatiquement.

Comportement

PUT /listings/:id
  • Le listing_id existe déjà : les deux étapes (Informations / Photos) sont librement accessibles, pas de verrouillage.
  • LIST-02 : modification réservée au propriétaire du bien — l'API doit vérifier owner_id = current_user.id, sinon 403.

Comportement

  • Tous les champs verrouillés pendant l'enregistrement (création ou édition).

Comportement

  • 422 validation → erreurs inline sous chaque champ concerné, plus une bannière générale en tête de formulaire.
  • Règles de validation précises (longueur min description, bornes prix/surface) non détaillées dans TECHNICAL_SPEC_MVP.md — valeurs illustratives ici, à confirmer côté backend.

Comportement

POST /media/upload
  • multipart/form-data avec listing_id + file. Validation par magic bytes (crate infer), jamais par extension déclarée (voir CLAUDE.md).
  • « Terminer » désactivé tant qu'aucune photo n'est présente (LIST-04 : 1 à 5 photos requises).

Comportement

PATCH /listings/:id/cover
  • LIST-05 : une couverture est obligatoire ; la première photo uploadée l'est par défaut (contrainte DB : index unique idx_listing_media_one_cover).
  • ⚠ Aucun endpoint de réorganisation (position) n'existe dans le contrat actuel — voir flag en bas de page.
  • Suppression de la photo de couverture bloquée tant qu'une autre n'a pas été désignée couverture au préalable (règle explicite §4.5).

Comportement

  • Chaque photo s'uploade indépendamment (une requête POST /media/upload par fichier) ; la progression est locale au FE, pas de endpoint de progress côté contrat.

Comportement

  • LIST-04 : maximum 5 photos par bien — la tuile « Ajouter » disparaît une fois la limite atteinte.

Comportement

  • Rejet local (avant appel réseau) si le type MIME détecté ou la taille ne respectent pas les contraintes LIST-04 ; sinon 422 renvoyé par le backend après vérification magic bytes.
  • Les photos déjà uploadées restent inchangées — l'erreur ne concerne que le fichier rejeté.

Comportement

GET /users/me/listings
  • LIST-06 : liste des biens du propriétaire connecté, quel que soit leur statut.
  • Bascule de statut → PATCH /listings/:id/status (LIST-03), optimiste côté FE avec rollback si erreur.
  • Badge de rappel (illustré sur la 1ʳᵉ ligne) : extrapolation UI de la notification « 1 mois » de LIST-03 — voir flag ci-dessous.
  • « Supprimer » nécessite une confirmation (modal non représentée dans ce wireframe).

Comportement

  • Aucun bien pour cet owner → CTA direct vers le formulaire de création.

Comportement

  • Squelette pendant GET /users/me/listings.

Décisions & hypothèses prises pendant cette session

⚠ Pas d'endpoint de réorganisation des photos Le contrat API expose POST /media/upload, DELETE /media/:id et PATCH /listings/:id/cover, mais aucun moyen de persister un nouvel ordre (position). Le drag-to-reorder est dessiné ici car demandé par le ticket, mais nécessite un nouvel endpoint (ex. PATCH /listings/:id/media/reorder) — à créer côté backend ou à retirer du scope FE si non prioritaire.
Flow de création en 2 étapes (Informations → Photos) Imposé par une contrainte technique, pas un choix produit arbitraire : POST /media/upload exige un listing_id existant. En édition, les deux étapes restent librement accessibles puisque le bien existe déjà.
Champs requis alignés sur les contraintes DB, pas sur le libellé du cahier des charges listings (DDL) : titre/description/type/ville/prix en NOT NULL ; surface, pièces et quartier nullables. LIST-01 les cite tous sans distinction — le wireframe suit la DB comme source de vérité, même logique que le champ téléphone dans MH-12.
Badge de rappel « mis à jour il y a X jours » illustratif LIST-03 décrit une notification envoyée à l'owner après 1 mois si le bien reste « disponible ». Le badge dans la liste « Mes biens » est une extrapolation UI pour rendre ce rappel visible aussi in-app — non explicitement demandé par le contrat, à valider avec le produit.
Suppression d'un bien sans modal de confirmation dans ce wireframe Le bouton « Supprimer » est représenté tel quel ; la confirmation (modal/dialog) est un composant partagé hors périmètre de ce wireframe bas-fidélité.
