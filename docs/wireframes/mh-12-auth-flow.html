Comportement

POST /api/v1/auth/otp/request
  • Un seul champ : email. Aucune distinction visuelle "connexion" vs "inscription" — l'API traite les deux cas de façon transparente (AUTH-02 / AUTH-03).
  • Validation basique du format email côté client avant l'appel (non spécifiée dans le contrat, à la charge du FE).
  • 200 → navigation vers l'écran Code OTP, email transmis en state (pas en query string).

Comportement

  • Champ email et bouton désactivés pendant l'appel réseau — empêche la double soumission.
  • Pas de timeout défini dans le contrat : prévoir un état d'échec réseau générique côté FE (hors périmètre visuel de ce ticket).

Comportement

POST /api/v1/auth/otp/request
  • 429 OTP_RATE_LIMITED → bannière + bouton désactivé avec compte à rebours.
  • Durée exacte du cooldown non précisée dans TECHNICAL_SPEC_MVP.md — logique exacte (TTL, nombre de tentatives) laissée au backend, à concevoir dans le ticket dédié.
  • L'email saisi reste visible (grisé) pour laisser le contexte visible à l'utilisateur.

Comportement

POST /api/v1/auth/otp/verify
  • 6 champs de saisie séparés (chiffres) — auto-focus séquentiel et soumission auto au 6ᵉ chiffre à prévoir en FE.
  • Lien de renvoi désactivé avec un cooldown initial (ex. 45s) pour limiter le spam avant même d'atteindre le rate-limit serveur.
  • "Modifier l'email" ramène à l'écran 1 avec le champ pré-rempli.

Comportement

  • Les 6 champs et le bouton sont verrouillés pendant la vérification.

Comportement

POST /api/v1/auth/otp/verify
  • 401 OTP_INVALID → message générique unique. Le contrat API ne distingue pas "invalide" de "expiré" (même code erreur) : impossible d'afficher un message différencié sans changement backend.
  • Les 6 champs sont vidés et repassent en focus sur le premier, pour ressaisie immédiate.
  • Nombre d'essais avant blocage et logique de rate-limit : géré côté backend, à concevoir dans le ticket dédié.

Comportement

POST /api/v1/auth/otp/request
  • Déclenché par un clic sur "Renvoyer le code" — réutilise le même endpoint que l'écran 1, donc peut aussi renvoyer 429 OTP_RATE_LIMITED.
  • Le code déjà reçu reste vérifiable : les champs de saisie ne sont pas verrouillés par cette bannière.

Comportement

PUT /api/v1/users/me
  • Affiché uniquement quand is_new_user = true dans la réponse de /otp/verify (PROF-02).
  • Email en lecture seule, pré-rempli depuis l'écran 1 — le changer nécessiterait un nouveau flow OTP, hors périmètre.
  • Prénom / nom requis. Téléphone facultatif à cette étape.

Comportement

  • Tous les champs verrouillés pendant l'enregistrement. Succès → redirection vers le feed (hors périmètre MH-12).

Comportement

  • Erreur de validation : message inline sous le champ concerné (ex. prénom vide) plutôt qu'une bannière générale — feedback localisé.
  • Une bannière générique ("Une erreur est survenue, réessayez.") reste à prévoir pour un échec serveur (500), non représentée séparément ici.

Décisions & hypothèses prises pendant cette session

Email en lecture seule à l'étape profil Pré-rempli depuis l'écran 1, non modifiable — évite de réintroduire un flow OTP à cette étape.
Téléphone ajouté en saisie manuelle facultative Écarte l'hypothèse d'un auto-remplissage (l'endpoint /otp/request ne collecte pas de téléphone). Décision produit prise en session — nuance la règle "téléphone renseigné uniquement lors de la demande owner" (database.md). Persiste via PUT /users/me existant, sans nouvel endpoint.
Un seul message d'erreur pour code invalide / expiré Le contrat API renvoie un unique 401 OTP_INVALID — aucune distinction possible côté FE sans évolution backend.
Rate-limit (durée, tentatives) laissé au backend Les valeurs de compte à rebours affichées (04:12, 02:30…) sont illustratives. La logique exacte (TTL, nombre de tentatives avant blocage) sera conçue dans le ticket backend dédié, pas dans ce wireframe.
