Comportement

POST /owner-requests
  • Soumission atomique en un seul appel multipart/form-data (phone, identity_data en JSON, documents[]) — décision déjà verrouillée dans CLAUDE.md : pas de brouillon, pas de flow en plusieurs étapes (contrairement à MH-14 pour les biens).
  • Cet écran n'est atteignable que si l'utilisateur n'a pas déjà de demande pending — sinon la vue Statut (écran 2) est affichée à la place (OWN-02).
  • 201 → navigation directe vers l'écran Statut, état « En attente ».

Comportement

  • Tous les champs verrouillés pendant l'envoi. Message explicite anti-fermeture de page pendant l'upload multi-fichiers (peut prendre plusieurs secondes).

Comportement

  • 422 INVALID_DOCUMENT → erreur inline sur le fichier concerné (format/taille), le reste du formulaire reste rempli.
  • Erreurs de validation de champ (téléphone, numéro de pièce requis) traitées côté FE avant l'appel réseau quand possible.
  • 409 OWNER_REQUEST_ALREADY_PENDING — cas limite (double clic, autre onglet) : rediriger vers l'écran Statut plutôt qu'afficher une erreur de formulaire.
  • Soumission atomique confirmée par le contrat : si un document échoue, rien n'est persisté côté serveur — cohérent avec le message affiché.

Décisions & hypothèses prises pendant cette session

⚠ Liste des types de pièce d'identité non spécifiée identity_data est un champ JSONB libre ({ full_name, id_type, id_number }) — aucune énumération canonique de id_type n'existe dans le contrat. Les options illustrées (CNI, Passeport, Permis de conduire) sont une proposition à valider, notamment pour couvrir les deux marchés (France + Afrique francophone).
⚠ Contraintes de format/taille des documents extrapolées Contrairement aux photos de listing et à l'avatar (JPEG/PNG/WebP, 5 Mo, explicitement documentés), §4.2bis ne précise pas les formats ni la taille max acceptés pour les documents d'identité. Le wireframe reprend par cohérence JPEG/PNG/PDF, 5 Mo — à confirmer côté backend avant implémentation.
Soumission unique atomique (pas de step comme MH-14) Contrairement au flow de création de bien (MH-14, en 2 étapes à cause de la contrainte listing_id), la demande Owner est un seul formulaire avec un seul bouton d'envoi — décision déjà verrouillée dans CLAUDE.md, pas une invention de cette session.
Forme de la réponse GET /users/me/owner-request reconstruite Aucun exemple JSON n'est fourni dans le contrat pour cet endpoint. Les champs affichés dans la vue Statut (téléphone, type de pièce, nombre de documents, dates) sont déduits des colonnes de la table owner_requests (DDL), à confirmer avec le backend.
Portée limitée au parcours Seeker OWN-04 (notification admin) et OWN-05 (écran de décision admin) concernent le dashboard Admin, hors périmètre de ce wireframe qui couvre uniquement le formulaire et la vue de statut côté utilisateur.
