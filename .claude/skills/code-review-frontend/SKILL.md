# Code Review — Frontend (React / TypeScript / MyHouse)

## Purpose

Produce a structured, consistent review of frontend changes: catch bugs, accessibility
gaps, and non-idiomatic React a tired human reviewer might miss — **and** verify the diff
respects the MyHouse frontend structure (feature-folder layout, generated types, no proxy
patterns for static media). Conversation in French, findings can cite English ticket terms
(MH-XX) directly.

Full checklists (React/TS idioms, accessibility, performance, MyHouse structure rules) live
in `reference/checklist.md` — load it before starting Phase 3. Don't paraphrase this file
from memory; read it fresh each time since it may be updated independently of this skill.

## When NOT to trigger

- Reviewing backend/Rust code → `code-review-backend`
- Writing/implementing a ticket → normal coding flow, not this skill
- Pure copy/microcopy changes with no logic → skip Phase 3's React-specific checks, do a
  light pass focused on UX copy correctness instead

## Process — Four Phases

Don't skip phases. Structural problems (wrong feature folder, hand-edited generated types)
are more important than line-level nits and should surface before you get there.

### Phase 1 — Context

- What ticket (MH-XX) does this PR close?
- What feature(s) does it touch? (`auth`, `listings`, `search`, `profile`, `contact`,
  `admin`, or `shared/`)
- Vertical slice matching the ticket, or scope creep into unrelated features? Flag scope
  creep as `important`.
- Read the diff in full once before commenting.

### Phase 2 — High-Level Review

- **Feature folder structure**: components in `features/<domain>/components/`, data hooks
  in `features/<domain>/hooks/` or co-located `api.ts` — not new top-level folders or logic
  dropped into `shared/` that actually belongs to one feature.
- **Generated types**: is `src/shared/api/types.ts` touched by hand in this diff? That file
  is generated by `openapi-typescript` and gitignored — any manual edit is `blocking`; the
  real fix is a backend `utoipa` annotation or a regenerate step.
- **State management fit**: is the right tool used for the job (local `useState` for local
  UI state vs. a data-fetching hook for server state)? No ad-hoc caching/dedup logic that
  duplicates what a data hook already does.
- **Route guards**: role-gated routes (`/admin/*`, owner-only forms) actually enforce the
  guard in `app/router.tsx`, not just hide UI conditionally while leaving the route
  reachable.

### Phase 3 — Line-by-Line

Load `reference/checklist.md` now. Go through: hooks rules, accessibility basics, TypeScript
strictness (no `any` smuggled in), performance (avoidable re-renders, missing memoization
only where it actually matters), copy/UX text quality.

### Phase 4 — Summary & Decision

Output the report (format below) directly in chat as markdown — never auto-post to GitHub
even if `gh` CLI is available, unless the person explicitly asks you to post it.

## Severity Labels

| Label          | Meaning                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------- |
| `blocking`   | Must fix before merge — bug, broken a11y, structural violation, security issue (XSS, etc.) |
| `important`  | Should fix — scope creep, missing loading/error state, weak typing with real cost          |
| `nit`        | Style/naming preference, no functional impact                                               |
| `suggestion` | Optional improvement, not required for this PR                                              |

## Report Format

```markdown
## Review — MH-XX (feature)

**Scope check:** [matches ticket / scope creep into <feature>]
**Structure check:** [clean / N violations — see below]

### Findings

**[blocking] path/to/Component.tsx:42**
<what's wrong, why it matters, suggested fix>

**[important] path/to/hook.ts:18**
...

### Summary
X blocking · Y important · Z nit/suggestion
Verdict: [approve / approve with comments / request changes]
```

## MyHouse-Specific Invariants (always check, even in a small diff)

- Listing photos and avatars are fetched directly from their stored `url` — never routed
  through a new backend call that re-serves file bytes. If a component adds a fetch to some
  `/api/.../file` style endpoint for a public image, `blocking`.
- The refresh token is never read, stored, or referenced in frontend JS/TS — it lives only
  in an `httpOnly` cookie the browser manages. Any code touching `document.cookie` for auth
  purposes, or storing a token in `localStorage`/`sessionStorage`, is `blocking`.
- `is_new_user` from `POST /auth/otp/verify` drives the profile-completion redirect — check
  that flow isn't bypassed or duplicated with a second heuristic.
- No hardcoded API URLs bypassing the shared `api/client.ts` instance — consistency for
  base URL, headers, and interceptor behavior (e.g. token refresh-on-401) depends on every
  feature going through it.
